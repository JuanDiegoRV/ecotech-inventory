# Arquitectura de EcoTech Inventory

EcoTech Inventory utiliza React, Vite y TypeScript para construir una interfaz modular. La estructura dentro de `src` separa la presentación, la lógica reutilizable, el estado compartido, los contratos de datos y la infraestructura externa. Esta división reduce el acoplamiento y ofrece a cada integrante del equipo un lugar claro donde ubicar nuevo código.

La carpeta `components` contiene exclusivamente componentes visuales. Sus subcarpetas representan niveles diferentes de reutilización: `common` para elementos genéricos, `inventory` para componentes del dominio de inventarios y `layout` para la composición general de la aplicación. Las pantallas completas vivirán en `pages`, que combinarán estos componentes sin asumir responsabilidades de acceso a datos.

La lógica reutilizable se concentra en `hooks`. Esta capa podrá coordinar estados, filtros, formularios y eventos de usuario, pero las operaciones persistentes pertenecerán a `services`. Los servicios encapsularán las consultas y mutaciones contra Supabase, evitando que las páginas o los componentes conozcan detalles de PostgreSQL, autenticación o transporte. La configuración futura del cliente quedará aislada en `config/supabase`, usando variables de entorno y evitando credenciales en el repositorio.

`context` se reserva para estado verdaderamente compartido, como la sesión, permisos o preferencias globales. Mantener esta regla evita convertir el contexto en un almacén indiscriminado y facilita localizar el origen de cada dato. `types` centraliza los contratos de TypeScript para que entidades, respuestas y parámetros mantengan una forma consistente. Las futuras tablas de Supabase utilizarán `snake_case`, por ejemplo `inventory_items` y `stock_movements`; los archivos seguirán `kebab-case`.

La metodología de Desarrollo Basado en Especificaciones (SDD) complementa esta organización. Cada funcionalidad debe definir primero su comportamiento, límites y criterios de aceptación antes de implementarse. Después, el código se coloca en la capa correspondiente y se valida contra esa especificación. Este flujo previene decisiones improvisadas, duplicación y dependencias ocultas, además de facilitar revisiones y pruebas. A medida que crezca el producto, la separación permitirá incorporar dominios, servicios o pantallas nuevas sin reescribir la base existente, reduciendo el riesgo de deuda técnica.
